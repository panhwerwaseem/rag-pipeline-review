# Building a labelled query set, and reading the metrics

`scripts/retrieval_eval.py` needs two files: the questions with the IDs that
should be retrieved for each, and what the pipeline actually retrieved. This
file covers how to build the first, how to export the second, and what the
numbers mean.

## File formats

Both files are JSONL (one JSON object per line) or a JSON array.

Query set, one record per query:

```json
{"id": "q17", "query": "Why can't a member see a colleague's invoices?", "relevant": ["kb/user-roles.md"]}
```

- `id`: unique within the file.
- `query`: the text sent to the pipeline. It is printed with each failing
  query and is part of the set's fingerprint.
- `relevant`: a list of IDs, or an object of ID to grade for graded relevance,
  for example `{"kb/user-roles.md": 2, "kb/sso-setup.md": 1}`. A grade of 0
  means not relevant. An empty list marks a question the corpus cannot answer;
  it is reported and left out of the averages.

Results, one record per query, best result first:

```json
{"id": "q17", "results": [{"id": "kb/user-roles.md#2", "doc_id": "kb/user-roles.md", "score": 6.1}]}
```

A result is a plain ID or an object. `--match-field` names the key that is
compared with the labels. Order in the list is the rank; a `score` key is
ignored.

## How many queries

Fewer queries means wider uncertainty. The table shows the 95% Wilson interval
for an observed hit rate of 0.80 at different set sizes. `retrieval_eval.py`
prints this interval for your own numbers.

| Queries | Observed hit rate | 95% interval |
|---|---|---|
| 5 | 0.80 | 0.38 to 0.96 |
| 10 | 0.80 | 0.49 to 0.94 |
| 20 | 0.80 | 0.58 to 0.92 |
| 50 | 0.80 | 0.67 to 0.89 |
| 100 | 0.80 | 0.71 to 0.87 |
| 200 | 0.80 | 0.74 to 0.85 |

With 10 queries, a true hit rate of 0.5 and one of 0.9 can both produce the
same result. The script warns below 20 scored queries. Treat 20 as the floor
for saying anything, and aim for 50 or more before comparing two
configurations whose difference is expected to be small. The interval assumes
the queries are a fair sample of real use, which is the next section.

## Where the queries come from

In order of preference:

1. **Real questions from logs or tickets.** Sample them at random, or evenly
   across topics and user types. Do not pick the ones you remember.
2. **Questions written by people who know the users.** Support staff, or
   whoever answers these questions today.
3. **Questions written from the documents.** Useful for coverage of documents
   nobody has asked about yet. They tend to reuse the document's wording, so
   they are easier to retrieve than real questions and make retrieval look
   better than it is. This applies to questions generated by a model from a
   chunk as well. Rewrite them in the user's vocabulary and record which
   queries were made this way.

Cover what real use contains: short keyword queries, long questions, typos,
identifiers and error codes, follow-up questions, questions that need two
documents, and questions the corpus cannot answer. Include known failures, but
do not let them dominate, or the set measures only the bad cases. Write down
how the set was collected. That description belongs in the review report.

## How to label

- **Find the relevant documents independently of the pipeline.** Use keyword
  search over the source, the table of contents, or a subject expert. If you
  label only by judging what the pipeline returned, a document it never
  returns can never be labelled relevant, and recall is overstated.
- **Label every document that answers the question**, not just the first one
  found. A missing label turns a correct retrieval into a false miss.
- **Choose the label level deliberately.**

| Level | Survives re-chunking | Shows whether the right passage came back |
|---|---|---|
| Document ID | Yes | No |
| Chunk ID | No. Chunk IDs change when the splitter changes | Yes |

  Use document IDs when the review will compare chunking or ingestion
  changes. Use chunk IDs when the splitter is fixed and passage-level precision
  matters. With document IDs, pass `--match-field doc_id`.
- **Use grades only if they mean something to you**, such as 2 for "answers
  the question" and 1 for "useful background". Grades affect nDCG only.
- **Have a second person check a sample** of the labels. Disagreement shows
  which questions are ambiguous; fix or drop those.

## Exporting the results

- Call the retrieval step as production does: same query preprocessing, same
  filters, same k or deeper.
- Save at least twice as many results as the k used in the prompt. The script
  can then tell "not retrieved at all" from "retrieved but ranked below k".
- Save the chunk ID and the document ID for each result.
- Keep one results file per configuration, and record what the configuration
  was.
- Running the pipeline for the export usually calls an embedding service. Get
  agreement first.

## What each metric means

For one query, with R the set of labelled IDs and the ranked results cut at k:

| Metric | Definition | Read it as |
|---|---|---|
| Hit rate@k | 1 if any of the top k results is in R, otherwise 0 | Share of queries where the prompt had a chance |
| Recall@k | labelled IDs found in the top k, divided by the size of R | How much of what was needed came back |
| Precision@k | top-k results that are in R, divided by k | How much of the context is useful. The divisor is k even when fewer results came back |
| MRR@k | 1 divided by the rank of the first result in R; 0 if none is in the top k | How high the first useful result sits |
| nDCG@k | DCG@k divided by the best possible DCG@k, where DCG@k is the sum of grade / log2(rank + 1) over the top k | Rank quality when there are several relevant IDs or grades |

Each reported number is the mean over the scored queries. Details that change
the numbers:

- **Ungraded labels have grade 1.** The script uses the grade itself as the
  gain. Another common nDCG variant uses 2 to the power of the grade, minus
  1. The two agree for ungraded labels and differ for graded ones, so name the
  variant when comparing with numbers from another tool.
- **Repeated IDs.** When labels are document IDs and results are chunks,
  several results can carry the same labelled ID. Recall and nDCG count that
  ID once, at its first rank. Precision counts every result that carries a
  labelled ID.
- **Precision has a ceiling.** With one labelled ID per query and no repeated
  IDs, precision@5 cannot exceed 0.2. Low precision is not a defect by itself.
- **A labelled query with no results record scores zero** and is reported as a
  blocking finding. It is not skipped.
- **The 95% interval** printed next to the hit rate is the Wilson score
  interval. The other metrics are printed without an interval.

## Comparing two runs

Run once with `--json` and keep the file, then run again with `--baseline`.
The script compares only runs with the same query-set fingerprint (IDs, query
texts and labels), the same largest k and the same match field.

For recall, MRR and nDCG at the largest k it counts the queries that got
better, got worse and stayed the same, and prints a two-sided sign test
p-value on the better and worse counts. A p-value of 0.05 or more means a
split that uneven happens often by chance with this many queries. Report that
as no measurable difference. A small p-value says the direction is unlikely to
be chance; it does not say the change is large, so report the size of the
change as well.

## Keeping the set honest

- Version the query set with the code. A changed label is a new set.
- Do not tune against the same set indefinitely. Settings chosen because they
  score well on these queries will look better here than on new ones. Keep a
  second set that is used only for a final check.
- Re-check the labels when the corpus changes. Removed and merged documents
  leave labels pointing at IDs that no longer exist, which shows up as
  `never-retrieved`.
- Add each real failure that users report as a new labelled query.
